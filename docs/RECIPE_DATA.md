# Recipe data: what the screens show vs what the database holds

Every element the recipe screens display, where it comes from today, and what
it needs. "Have" means loaded for all 400 recipes. Written for the database
design pass Naveen asked for.

## Recipe detail screen

| On screen | Where it lives | Status | Plan |
|---|---|---|---|
| Title, description | `recipes.recipe_name`, `recipe_description` | Have | |
| Prep time, cook time, servings, difficulty | `recipes.prep_time_min`, `cook_time_min`, `servings`, `difficulty_level` | Have (difficulty empty for Food.com) | Derive difficulty from step count and total time, one-time |
| Nutrition facts panel | `recipe_nutrition` per serving, from Food.com | Have, static | Becomes dynamic: `fn_recipe_nutrition(recipe_id, overrides)` recalculates from ingredient grams, so a swap or quantity change updates the panel |
| Iron, calcium, vitamins and other micros | `mv_recipe_nutrients` derived from `ingredient_nutrition` (USDA) | Have, approximate | Better once ingredient units are parsed |
| Probiotics, antioxidants, omega-3 | nothing | Missing, not in USDA | Tag ingredients in `ingredient_attributes` (yogurt = probiotic, salmon = omega-3, berries = antioxidant) from a keyword list, then a recipe has the tag if any ingredient does. One-time |
| Meal type, dietary tags | `recipes.meal_category`, `dietary_tags` | Have | |
| Cuisine (Mediterranean, Asian) | `recipes.cultural_category_id` and `cultural_categories` | Table exists, column empty | Fill from Food.com Keywords (Asian, Mexican, Greek, ...), one-time. Fallback: AI classification for the rest |
| Image | `foodcom_recipes_raw.images` has URLs | Have in raw, not on `recipes` | Add `recipes.image_url`, copy first URL. One-time |
| Ingredients with quantities | `recipe_ingredients` joined to `ingredients` | Have quantities, no units | Parse units from the original text (`foodcom_recipes_raw.recipe_ingredient_quantities` and parts) into grams per line. Unparseable lines stay NULL and are flagged |
| Organic, non-GMO, allergen labels | `ingredient_attributes` (exists), `ingredients.is_allergen` (have) | Table exists, mostly empty | Allergen labels: have. Organic/non-GMO is a property of what you buy, not the recipe; show as a shopping note, not stored per recipe |
| Instructions | `recipe_steps`, 3,100 steps | Have | Cook screen doesn't display them yet |
| Synergies ("Vitamin C + Iron") | `nutrient_rules` (5 loaded) and `recipe_rules_map` (empty) | Table exists, not filled | Rule-based batch: for each recipe check ingredients against each rule, write `recipe_rules_map`. Deterministic |
| Bioavailability tip | `ingredient_nutrition.bioavailability_pct` (a few rows), rules above | Missing per recipe | AI-generated once per recipe from its ingredients and matched rules, stored and reviewed. See `recipe_content` below |
| Ingredient swap insight | nothing | Missing | AI-generated once per recipe, stored. Same table |
| Nutrient story ("Protein first", "Omega support") | nothing | Missing | Derived, not stored: top 3 nutrients by share of target from `mv_recipe_nutrients`. No AI needed |
| Badge ("AI Recommended for You", "Family Friendly") | nothing | Missing | Derived from the recommender at request time (score rank, household min score). Not stored |
| Favorite | browser only | Missing | New table `member_favorites` |

## New tables

Three small ones. Everything else fits existing tables.

```
recipe_content        recipe_id, kind ('bioavailability_tip' | 'swap_insight'), text,
                      model, generated_at, reviewed_by, reviewed_at
                      one row per recipe per kind, regenerated by a batch job

member_favorites      member_id, recipe_id, created_at

member_daily_note     member_id, note_date, text, model, generated_at
                      one per member per day, written by a nightly job

hydration_log         member_id, log_date, glasses
sleep_log             member_id, log_date, hours
member_achievements   member_id, achievement_code, unlocked_at
```

AI-generated text goes in its own table with the model name and a reviewed
flag, never in `recipes`. Facts (nutrients, rules) stay the source of truth;
the text is wording on top of them, and can be regenerated without touching
anything else.

## Where the AI runs

| Job | When | Input | Output |
|---|---|---|---|
| Rule matching | one-time, rerun when rules change | recipe ingredients, `nutrient_rules` | `recipe_rules_map` (no AI, pure rules) |
| Bioavailability tip | one-time per recipe, batch | ingredients, matched rules | `recipe_content` |
| Swap insight | one-time per recipe, batch | ingredients, allergens | `recipe_content` |
| Cuisine tag | one-time, only where keywords don't say | title, ingredients | `recipes.cultural_category_id` |
| Daily reflection | nightly per member | yesterday's log, today's gaps, streaks | `member_daily_note` |

Batch jobs are Python scripts in `scripts/`, same pattern as the importer,
runnable by anyone with the database and an API key.

## Order

1. Ingredient grams from the Food.com text, then per-serving nutrition recomputed from them with a coverage figure per recipe. Three or four days.
2. Source tracking: `data_sources`, `ingredient_source_map`, `source_id` on nutrition rows. A day, with USDA as the only source.
3. `fn_recipe_nutrition` for the dynamic panel, and the recipe screen showing ingredients, steps and the panel. Two days.
4. Meal logging with nutrient snapshot. Two days.
5. Cheap one-time fills: image URL, cuisine from keywords, difficulty, probiotic/omega/antioxidant tags, rule matching into `recipe_rules_map`. Two days.
6. New tables and favorites. A day.
7. Raw/cooked variants, starting with the most used ingredients. Ongoing.
8. AI batch for tips and swaps, with review. Two days plus review time.
9. Daily reflection job, once sign-in exists (needs a real member).

## Calculation rules from the nutrition flow

From the nutrition data flow document (Oct 2026). These apply to everything
above.

Nutrition per recipe is per-100g value x grams / 100 for each ingredient line,
summed, divided by servings. Each person's logged portion multiplies that.
Missing values stay NULL, never 0, and each recipe carries a coverage figure
(share of ingredient grams with full nutrient data).

Ingredients get a preparation state (raw, cooked, ...) so a line can point at
the right variant. Cooking losses are applied once, never to values that
already represent cooked food.

Every nutrient value carries its source. New tables `data_sources` (name,
version, license, attribution text) and `ingredient_source_map`
(ingredient_id, source_id, source_record_id); `ingredient_nutrition` gets a
`source_id`. USDA is first in precedence; other sources fill gaps. Attribution
is tied to the ingredient, not the recipe.

Logging a meal saves a nutrient snapshot per person. Editing a recipe later
does not change past meals.

Targets are versioned by effective date. A profile edit or an age-band change
creates a new target set; old ones stay for history.

On screen a shortfall is a gap against a target, not a deficiency.
