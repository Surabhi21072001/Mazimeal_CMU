# MaziMeal API

The backend exists for the two things the database cannot do on its own:
serving the **rule matches** on a recipe, and writing the **suggestion text**
that goes with them. Recipes, nutrition and meal logging stay with the
functions the other team already wrote.

The contract is `SPEC.md`. The fixtures are `fixtures/`, generated by
`build_fixtures.py`.

## Run it

```bash
python3.12 -m venv api/.venv
api/.venv/bin/pip install -r api/requirements.txt
cd api && .venv/bin/uvicorn app.main:app --reload --port 8000
```

Then point the frontend at it:

```bash
VITE_API_BASE_URL=http://127.0.0.1:8000 npm run dev --prefix web
```

Without that variable the frontend uses its bundled fixtures and shows a
"Sample data" badge, which is how it is deployed for the client.

## Switches

Everything is an environment variable, so no file needs editing.

| Variable | Default | What it does |
|---|---|---|
| `MAZI_REPO` | `fixture` | `fixture` reads `fixtures/*.json`. `supabase` is not written yet; it needs our own project first |
| `MAZI_PROVIDER` | `template` | who writes the suggestion text: `template`, `local`, or `api` later |
| `MAZI_LLM_URL` | `http://127.0.0.1:11434/v1` | any OpenAI-compatible endpoint (Ollama `:11434/v1`, mlx-lm `:8080/v1`) |
| `MAZI_LLM_MODEL` | `mlx-community/gemma-3-4b-it-4bit` | the model to call |
| `MAZI_LLM_TIMEOUT` | `60` | seconds; a cold model needs more |
| `MAZI_CORS_ORIGINS` | localhost dev ports | comma separated |

## How suggestions are written

`template` is the default **and** the fallback. It rearranges the rule's own
words: `engine_action` + `why`, ordered so a change the cook can make comes
before an explanation of something already true. No model runs, so nothing can
be invented. Rules marked `needs_review` never reach the cook screen; they are
for the reviewer console.

`local` sends each template sentence to a small model and asks only for a
rewrite. Two guards decide whether the rewrite is used:

- **No new numbers.** Any digit in the output that was not in the input means
  the model invented something, and the template text is kept instead.
- **It has to read like prose.** Empty answers, refusals, bullet lists and JSON
  are rejected.

If every rewrite fails, the response says `"source": "template"` rather than
claiming a model wrote it. The frontend shows that badge as-is.

## Running a local model

Homebrew cannot install packages on this machine (it reports a Tier 3
configuration), so Ollama is not installed. mlx-lm is, and on Apple Silicon it
is the faster path anyway. Both speak the same OpenAI-compatible API, so the
backend does not care which one is running.

```bash
# serve a model (downloads on first run, ~2.4 GB for 4B at 4-bit)
api/.venv/bin/python -m mlx_lm.server --model mlx-community/gemma-3-4b-it-4bit --port 8081

# point the backend at it
cd api && MAZI_PROVIDER=local MAZI_LLM_URL=http://127.0.0.1:8081/v1 \
  MAZI_LLM_MODEL=mlx-community/gemma-3-4b-it-4bit \
  .venv/bin/uvicorn app.main:app --port 8000
```

With Ollama instead, the only change is `MAZI_LLM_URL=http://127.0.0.1:11434/v1`
and a model name like `gemma3:4b`.

### What the models did on the four falafel rules

Measured on 2026-10-19, warm model, same prompt and guards.

| | invented a claim | got a fact wrong | left text unchanged | per suggestion |
|---|---|---|---|---|
| template | - | - | n/a | instant |
| Qwen2.5 0.5B | 1 of 4 | 1 of 4 | 1 of 4 | ~1 s |
| Gemma 3 4B | 0 of 4 | 0 of 4 | 0 of 4 | ~2.2 s |

The 0.5B added "enhancing the flavor and aroma" to the garlic rule and wrote
that tea and coffee "absorb iron", which inverts the mechanism. Neither was
caught by the number guard, because neither touched a number: a rewrite can be
wrong without being numerically wrong. Gemma 3 4B kept every fact and reads
better than the template.

A local model cannot follow the app to a hosted demo. That is fine: the
deployed build falls back to `template`, which is the version we are happy for
anyone to read.

## Pre-generated text and review

The suggestion text belongs to the **recipe**, not to the person reading it:
the rules matched the recipe and the rules supply the facts. What differs per
member - how much iron they still need, which recipe ranks first - is computed
and never written by a model. That is what makes pre-generating possible.

```bash
# run the model once over the sample recipes, offline. What it writes becomes
# version 1 of each recipe's review record - the baseline, never served to a cook
set -a; . ./.env; set +a
MAZI_REPO=supabase MAZIMEAL_DSN="$SUPABASE_DB_URL" \
  MAZI_PROVIDER=local MAZI_LLM_URL=http://127.0.0.1:8081/v1 \
  MAZI_LLM_MODEL=mlx-community/gemma-3-4b-it-4bit \
  api/.venv/bin/python api/pregenerate.py
```

Then review them on `#/review`, signed in and on the reviewer list. Each
decision appends a version; see `GET /api/review/content/{recipe_id}` in
SPEC.md.

What the suggestions endpoint serves, in order:

1. **reviewed** text, when a reviewer's current decision is to publish it. It
   wins over everything.
2. **cache**, when the same recipe and rules were rewritten before.
3. the **model**, otherwise - and the result goes into the cache.

`?refresh=true` skips 1 and 2 and rewrites. That is the Regenerate button on
the cook screen: a tester can see what the model writes now, and it changes
nothing for anyone else, because only a reviewed version is served to them.

Two cases deliberately fall through to 2 and 3: a recipe that only has the
model's own baseline (nobody has decided anything about it, so it must not read
as "reviewed"), and one whose newest decision is **rejected** (the screen says
nothing is published for it, so nothing is).

This used to be a file per recipe under `api/content/`, read ahead of the
cache. It is `recipe_content_versions` now - the same store the review screen
writes - because the file store could neither say who approved the text nor
survive a deploy on a host with no disk.
