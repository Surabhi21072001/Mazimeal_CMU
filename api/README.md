# MaziMeal API

The backend exists for the two things the database cannot do on its own:
serving the **rule matches** on a recipe, and writing the **suggestion text**
that goes with them. Recipes, nutrition and meal logging stay with the
functions the other team already wrote.

**Every endpoint, its input, its output and what an account is needed for is in
[docs/API.md](../docs/API.md).** This file is how to run the thing.

## Run it

```bash
python3.12 -m venv api/.venv
api/.venv/bin/pip install -r api/requirements.txt
api/.venv/bin/uvicorn app.main:app --app-dir api --reload --port 8002
```

Then point the frontend at it:

```bash
VITE_API_BASE_URL=http://127.0.0.1:8002 npm run dev --prefix web
```

Without that variable the frontend uses its bundled fixtures and shows a
"Sample data" badge. Against the live database, add a DSN — see
[docs/DATA.md](../docs/DATA.md) for where the connection string comes from:

```bash
set -a; . ./.env; set +a
MAZI_REPO=supabase MAZIMEAL_DSN="$SUPABASE_DB_URL" \
  api/.venv/bin/uvicorn app.main:app --app-dir api --port 8002
```

`GET /api/health` says which of those is live.

## Switches

Everything is an environment variable, so no file needs editing.

| Variable | Default | What it does |
|---|---|---|
| `MAZI_REPO` | `fixture` | `fixture` reads `fixtures/*.json`. `supabase` reads the live database and is what production runs; it needs `SUPABASE_DB_URL` (or `MAZIMEAL_DSN`) |
| `MAZI_ADMIN_EMAILS` | unset | comma-separated backstop reviewer list, unioned with the `app_admins` table. Nothing a request can change |
| `MAZI_PROVIDER` | `template` | who writes the suggestion text: `template`, `local`, or `api` (a hosted model, for the small-versus-large comparison) |
| `MAZI_LLM_URL` | `http://127.0.0.1:11434/v1` | any OpenAI-compatible endpoint (Ollama `:11434/v1`, mlx-lm `:8080/v1`) |
| `MAZI_LLM_MODEL` | `mlx-community/gemma-3-4b-it-4bit` | the model to call |
| `MAZI_LLM_TIMEOUT` | `60` | seconds; a cold model needs more |
| `MAZI_CORS_ORIGINS` | localhost dev ports | comma separated |
| `MAZI_CORS_ORIGIN_REGEX` | unset locally; set in `render.yaml` | the host pattern that lets the deployed frontend and its preview URLs call this |

The fixtures are `fixtures/`, generated by `build_fixtures.py`.

## How the suggestion text is written

`template` is the default **and** the fallback, and it is what production runs
— `/api/health` reports `"provider": "template"` and `"model": null`. It
rearranges the rule's own words: `engine_action` + `why`, ordered so a change
the cook can make comes before an explanation of something already true. No
model runs, so nothing can be invented. Rules marked `needs_review` never reach
the cook screen; they are for the reviewer console.

`local` sends each template sentence to a small model and asks only for a
rewrite. Two guards decide whether the rewrite is used: any digit in the output
that was not in the input means the model invented something, and empty
answers, refusals, bullet lists and JSON are rejected. If every rewrite fails,
the response says `"source": "template"` rather than claiming a model wrote it,
and the frontend shows that badge as-is.

Both guards are necessary and neither is sufficient. Comparing a 0.5B against a
4B on four falafel rules, the small model wrote that tea and coffee "absorb
iron", which inverts the mechanism and passes the number guard untouched: **a
rewrite can be wrong without being numerically wrong.** That is what the human
review step below is for.

To serve a local model, point the three `MAZI_LLM_*` variables at it — mlx-lm
(`python -m mlx_lm.server`) and Ollama both speak the same OpenAI-compatible
API, so the backend does not care which is running.

## Pre-generated text and review

The suggestion text belongs to the **recipe**, not to the person reading it:
the rules matched the recipe and the rules supply the facts. What differs per
member — how much iron they still need, which recipe ranks first — is computed
and never written by a model. That is what makes pre-generating possible.

```bash
# run the model once over the recipes, offline. What it writes becomes version 1
# of each recipe's review record - the baseline, never served to a cook
set -a; . ./.env; set +a
MAZI_REPO=supabase MAZIMEAL_DSN="$SUPABASE_DB_URL" \
  MAZI_PROVIDER=local MAZI_LLM_URL=http://127.0.0.1:8081/v1 \
  api/.venv/bin/python api/pregenerate.py
```

Then review them on `#/review`, signed in and on the reviewer list. Each
decision appends a row to `recipe_content_versions`.

What the suggestions endpoint serves, in order:

1. **reviewed** text, when a reviewer's current decision is to publish it. It
   wins over everything.
2. **cache**, when the same recipe and rules were rewritten before.
3. the **model**, otherwise — and the result goes into the cache.

`?refresh=true` skips 1 and 2 and rewrites. That is the Regenerate button on
the cook screen: a tester can see what the model writes now, and it changes
nothing for anyone else, because only a reviewed version is served to them.

Two cases deliberately fall through to 2 and 3: a recipe that only has the
model's own baseline (nobody has decided anything about it, so it must not read
as "reviewed"), and one whose newest decision is **rejected** (the screen says
nothing is published for it, so nothing is).

This used to be a file per recipe under `api/content/`, read ahead of the
cache. It is `recipe_content_versions` now — the same store the review screen
writes — because the file store could neither say who approved the text nor
survive a deploy on a host with no disk.
